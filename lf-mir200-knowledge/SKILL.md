# 翎风引擎 Mir200 知识库

## 概述

以**用户为当前服务端确认的对应版本说明书**作为语法和字段权威；技能随附说明书只在确认是对应版本后作为权威使用。把本地的 `样本Mir200/` 服务端脚本当作当前项目的实战写法参考——回答前先检索它，并优先采用其中的写法来处理项目专属实现。引用要落到本地文件路径，并区分「该版本说明书的官方行为」与「从样本推断出的结论」。

本技能还会从真实样本脚本中学习出一套**脚本思维模型**。该模型由样本脚本重新生成，应视为「实践中 Mir200 脚本是如何组织的」的持续更新摘要。

技能内含一份生成的训练课程。在做出宽泛结论或设计复杂脚本改动之前，按课程顺序在真实样本上练习。

**不要编译、启动或运行 Mir200 服务端。** 除非用户明确解除该约束，否则只做静态分析。

## 首次接入门槛（必须先确认）

每次第一次接入一个服务端，或用户更换底板，都先向用户确认下面四项；四项没有确认完，不写脚本、不猜素材、不执行数据库改动：

1. **服务端位置**：必须定位到包含 `Envir` 的那一层，并确认实际服务端根目录。
2. **客户端位置**：确认与该服务端配套的客户端资源目录。
3. **补丁位置与优先级**：确认要扫描哪些补丁、补丁加载顺序，以及同名资源由哪一份覆盖哪一份。
4. **对应版本的翎风引擎说明书**：确认说明书目录、版本标识或用户明确提供的章节集合。

严格使用用户确认的那一版说明书来写代码、脚本命令和数据解释。当前技能自带的说明书只能作为候选参考；如果版本不一致、章节缺失或用户没有确认版本，先停在核对阶段并说明缺口。不要把上一个服务端、上一个客户端、上一个补丁或另一版说明书的结论自动带入新项目。

把确认结果作为当前项目模型保存为四元组：

`服务端路径 → 客户端路径 → 补丁路径/优先级 → 说明书版本/路径`

后续所有脚本、数据库字段和素材编号都要能回溯到这组项目事实。素材接入和四类图片的读取规则见 [`references/material-assets.md`](references/material-assets.md)。

## 知识在哪里

技能根目录就是包含 `knowledge_base/index.md` 的那个目录：

- `knowledge_base/` —— 849 章翎风引擎说明书，由原始 CHM 转换而来。只读参考。
- `样本Mir200/` —— **可选**的本地服务端脚本样本。公开仓库不包含它（可能涉及私有服务端文件），需要样本分析时自行放入。
- `references/` —— 提炼后的规则与深挖记录，按需读取。
- `scripts/lf_kb.py` —— 索引、检索、查看、学习工具，只用标准库。
- `.lfmir-kb/indexes/` —— 生成的索引。用 `update` 重建，**不要手改**。

`样本Mir200/` 可以是真实目录，也可以是指向实机服务端根目录的**目录联接**（推荐后者：服务端更新后索引跟着更新，不必重复拷贝）。

始终带显式 root 运行，这样在任何工作目录下都可用：

```powershell
python "<skill-dir>\scripts\lf_kb.py" --root "<skill-dir>" validate
```

技能若移位，可用环境变量 `LF_MIR200_KB_ROOT` 覆盖 root 发现逻辑。脚本也会自动在祖先目录、`codex-skills/`、`skills/`、`~/.zcode/skills/`、`~/.agents/skills/` 里寻找知识根。

## 标准工作流

1. 先完成上面的首次接入门槛，锁定当前项目的四元组。
2. 对当前说明书和样本运行 `validate`；索引为空或来源变动时，按实际来源重建索引。自带 `lf_kb.py` 的 `update` 只索引技能内的说明书，不会自动切换到用户另给的一版；另一版需单独检索或先建立相应索引。
3. 读项目自己的说明文件（通常是 `AGENTS.md`），了解编码、编译/运行限制、归属边界与静态检查方式；再读用户提到的设计文档。
4. 在**已确认版本**的说明书里检索命令语法、字段含义和官方行为。
5. 在 `样本Mir200` 里检索可用写法；把样本推断出的结论标注出来。没有样本时，明确说明「样本推断不可用」。
6. 需要从样本学习或改进本技能时，读 `references/mir200-training.md`。
7. 读 `references/mir200-thinking.md` 获取当前本地脚本思维摘要。
8. 用户点名要深挖某个脚本时，读 `references/script-deep-dives.md`。
9. 涉及 PAK/WIL/WZL 素材、装备外观、内观、背包图、掉落图或用户明确要求入库时，读 `references/material-assets.md`，并按项目补丁优先级直接读取素材。
10. 涉及 `@标签(参数)`、`<$SCRIPTPARAM*>`、`CHECKSCRIPTPARAM`、`GOTO @label(args|returns)` 这类标签或 UI 链接写法时，读 `references/script-parameters.md`。
11. 涉及 `Envir` 下 `.txt` / `.ini` 配置表（而非仅 NPC 对话脚本）时，读 `references/envir-config-rules.md`。
12. 用户点名要深挖某个 `Envir` 配置文件时，读 `references/envir-config-deep-dives.md`。
13. 涉及功能型 BUFF、觉醒之印、流派、铭文式自定义属性、宠物契约、流派化 BUFF 体系时，读 `references/sample2-feature-buffs.md`。
14. 涉及颜色值、`0-255` 色板、`/SCOLOR`、`{文字|颜色}`、装备名字颜色、物品备注、套装备注、自定义物品文字颜色、自定义属性、进度条、怪物名字颜色、稀有度配色时，读 `references/mir200-256-colors.md`。
15. 日志报 `[脚本死循环]`、反复 `GOTO` 失败、`QManage` 定时器失败，或某脚本在刷新/调用链变长后开始报错时，读 `references/script-deadloop-debugging.md`。
16. 涉及英雄宝宝/英雄宠物（英雄 `RECALLMOB`、`H.RECALLMOB`、`CHECKSLAVECOUNT`、`@HeroLearnMagic`、`@OnHeroSlaveDie`、`@HeroSlaveAttack`、英雄召唤技能）、英雄宠物数量/占用、自动召唤功能时，读 `references/hero-autocall-slave.md`。
17. 下结论或动手改之前，先看最相关的项目文件。
18. 改脚本时保持原编码与风格，只改用户要求改的文件。
19. 改完做静态验证：跑 `validate` 并做定向检索。

## 规则来源边界（重要）

下面的耐久规则来自**多个不同的服务端**。把某条规则用到错误的服务端上，是本技能最主要的翻车方式，所以用之前先确认来源：

- **引擎级规则** —— 关于已确认版本说明书收录的命令、触发、变量族、`Envir` 表语法的规则。它们仅对与该说明书匹配的引擎版本成立；其他版本必须重新核对。
- **样本项目规则** —— 提到具体项目的标签、物品、文件或阶段变量的规则（例如 `老登` 系列模块、`样本2Mir200` 的流派与觉醒体系、分阶段开图的阶段变量）。这些描述的是**某一个**服务端。把它们当作待核对的**结构范式**，绝不能当作当前服务端的事实。

当某条规则提到具体项目的标签、物品或文件时，**先确认它在当前服务端存在**，再据此给建议。凡是本项目没有的机制，不要因为技能里写了就假定它存在。

## 耐久规则

### 编码与读取

- Mir200 项目文本默认按 **ANSI** 读。若出现乱码，改试 UTF-8。写回文件时必须保持原编码。
- `Mir200/Envir/**/*.txt` 通常是 GBK/ANSI，必须用保编码的工具编辑。`AGENTS.md`、`docs/`、知识类 Markdown 用 UTF-8。

### 触发与回调

- `[@OnKillMob]` 要求目标地图在 `MapInfo.txt` 里带 `ONKILLMON`。
- `[@KillMon]` 不需要 `ONKILLMON`，不要与 `[@OnKillMob]` 混用。
- `QFunction-0.txt` 里的标签是**引擎回调**：`@ButtonClickX` 来自 `ADDBUTTON`，`@CustomButtonClick` 来自预留 UI 按钮，`@MinMapCustomButtonClickX` 来自小地图按钮，`@StdModeFuncX` 来自物品 `AniCount`，`@ItemUpgrade` 来自宝石升级，`@AddBag` 来自物品入包。未经查证官方触发章节，不要改名或挪作他用。
- 官方 `667-物品进入背包触发.md` 明确警告：不要在 `@AddBag` 里直接写回收逻辑。应派发到有守门的辅助脚本，让捡取/关联/刷新行为保持窄范围。
- `SetOnTimerEx` 启动的毫秒定时器触发 `MapQuest_def/QManage.txt` 里的 `[@OnTimerExX]`；普通 `SetOnTimer` 触发 `[@OnTimerX]`。改定时器 ID 或间隔前，起点与 QManage 处理端都要一起审。
- 个人定时器要把功能脚本里的 `SetOnTimer n 秒` / `SetOffTimer n` 与 `MapQuest_def/QManage.txt` 里的 `[@OnTimer<n>]` 配对。不要只改一边。

### 怪物与地图

- Boss 或首杀逻辑必须匹配 `MonGen.txt` 里的**完整怪物名**。不要静默忽略数字、方括号或其他后缀。
- 同一怪物名出现在多张地图时，改动全局进度前还要检查当前地图和相关的阶段/状态变量。
- 从项目数据判定 Boss 时，要把 `MonGen.txt` 的刷新密度与怪物数据库（常见为 `Mud2/DB/GEEM2.db`，表 `Monster`）交叉核对。除非项目有显式 Boss 名单，否则结论按**启发式**处理。
- 强 Boss 候选通常具备：在本图处于最高一到两个等级档、刷新稀少或间隔长、HP/攻击/防御相对同图其他怪显著偏高。名字含 `教主`、`魔王`、`恶魔`、`尸王`、`[BOSS]`、`暗之`、`触龙神`、`黄泉`、`双头`、`蛛王`、`地藏王`、`重装使者`、`王` 是**旁证而非充分证据**。
- 精英/头目类要单独归类：`卫士`、`将军`、`祭司`、`[精英]`、`[头目]`、`[狂化]` 或区域变体这类高等级稀有怪，除非地图语境确认它就是本图顶级稀有遭遇，否则不要套用 Boss 专属的平衡处理。
- 把明显的功能怪/守卫怪排除出 Boss 推断，例如城里的 `弓箭守卫`、`恶魔弓箭手`、训练/测试怪，以及其他非打猎用途的怪，即使它们等级很高。
- 平衡怪物数值时，按数据库中存储、`MonGen.txt` 中刷出的**精确怪物名**分类，不要把后缀变体合并，例如 `牛魔王`、`牛魔王8`、`沃玛教主`、`沃玛教主1`。
- 怪物强化任务要先看 `Monster` 表结构再改值。`GEEM2.db` 里可用字段包括 `Lvl`、`HP`、`AC`、`MAC`、`DC`、`DCMAX`、`MC`、`SC`、`SPEED`、`WALK_SPD`、`ATTACK_SPD`。
- `MapInfo.txt` 里形如 `0 308,264 -> 0102 3,7` 的行是**地图链接**：踩到源地图 `0` 的 X308 Y264，进入目标地图 `0102` 的 X3 Y7。坐标可能写作 `X,Y` 或 `X Y`，两种都要能解析。
- 地图链接是**有方向的**。除非存在单独的反向链接（通常在相邻坐标上），否则不要假定存在回程。
- 动态地图链接优先用说明书收录的引擎命令，不要猜语法。本地说明书在 `knowledge_base/chapters/049-动态地图连接.md` 记录了 `ADDMAPGATE`、`DELMAPGATE`、`GETMAPGATE`；生成动态链接前先看这一章。
- 分阶段开图设计要**堵住每一条进入路径**，不能只堵 NPC 传送菜单：`MapInfo` 链接、`MAPMOVE`/`MAP`/`MAPS`/`GROUPMAPMOVE`、召回与换图命令、动态地图、活动、物品传送、随机移动、重连/死亡/复活路径、机器人脚本，以及 GM/管理员绕过。
- 分阶段开图的自然 `MapInfo.txt` 链接（低阶段地图指向高阶段地图）是潜在绕过口，要按方向解析。
- 动态替换链接在重建前要先清理（`DELMAPGATE`），然后只按当前阶段允许的范围重建（`ADDMAPGATE`）。
- 启动或环境初始化可能影响全局变量，所以依赖阶段的动态链接要在初始化后、以及阶段推进成功后刷新。
- `Market_def/QMission-0.txt` 是特殊的任务页显示脚本。不要用 `GOTO @label` 派发来构建「当前状态」显示页；在该语境下 `GOTO` 可能无法显示目标内容。应使用菜单链接如 `<当前世界进度/@世界当前进度>`，并把每个条件 `#SAY` 分支直接写在所选标签下，匹配分支以 `#ACT` / `BREAK` 收尾。
- `QMission-0.txt` 任务页应优先用直接标签而非派发标签。进度页要在同一标签内重复 `#IF EQUAL ... n` / `#SAY ...` / `#ACT BREAK`，固定详情页用 `<文本/@标签>` 链接保持可达。
- 后期世界分裂到多张地图时，把阶段变量当作**阶段序列**而非单一的「全开」桶。

### Envir 配置表

- `Envir` 下的 `.txt` 和 `.ini` **不是同一套语法**。解析或编辑前先分类文件族：地图表、刷怪表、NPC 放置表、地图事件表、机器人排程、掉落表、允许/禁止名单、分节配方、宽行物品规则，或 INI 分节键值文件。
- 配置表里**路径和文件名常带运行时含义**。不要只凭显示名猜目标脚本或数据文件；遵循 `MerChant.txt`、`Npcs.txt`、`Robot.txt`、`AutoRunRobot.txt`、`MapEvent.txt`、`MonItems/<怪名>.txt`、`SmartMonster/<怪名>.ini`、`UserData/CustomSkill/<id>.ini` 的登记规则。
- 像 `MonGen.txt` 这类空白分隔的表要**保持可选字段的位置**。若需要靠后的可选字段，必须给靠前的可选字段留占位值，而不是把列左移。
- 配置里的分号注释是非活动数据，但常是有用的结构线索。空列表文件与空配置目录可能是有意的占位，不要仅因样本里没有活动行就删掉它们或推断某功能不可能实现。
- `TzItemDescList.txt` 控制玩家可见的**套装备注**，不是实际套装效果。声称需求件数或数值效果前，先交叉核对 `GroupItemList.txt`；备注里括号内的逗号组是**同部位替代项**，不是额外需求件。
- `GroupItemList.txt` 与 `GroupItemSkillPowerList.txt` 才是**运行时套装加成来源**。保持其固定数组里每个 `|` 零占位符，按套装 ID 关联技能威力段，`TzItemDescList.txt` 仅作显示层交叉核对。
- `ItemRuleList.txt` 是 M2 `列表信息2 -> 物品规则` 背后的运行时物品规则表；`ItemDescList.txt` 是玩家可见的物品备注文本。不要仅凭备注推断交易/掉落/修理/存仓限制；要交叉核对规则表、脚本触发与项目禁止名单。
- `EffectImageList.txt` / `EffectItemList.txt` / `EffectList.txt` 要分层验证：特效资源、物品默认特效、脚本可调用特效是三层不同的东西。
- 涉及「是否可交易、可丢弃、可修理、可升级、是否触发 QFunction、套装是否真正生效」的判断，必须交叉验证运行时配置、脚本触发和官方说明，**不能只看备注文本**。
- `Robot.txt` 只把机器人名绑定到 `Envir\Robot_def\AutoRunRobot.txt`；而 `AutoRunRobot.txt` 的条目要经 `Envir\Robot_def\RobotManage.txt` 解析，所以新增一个排程标签需要在 `RobotManage.txt` 里有对应的 `[@tag]`，由它再 `#CALL` 真正的脚本。
- `RobotManage.txt` 里的机器人排程标签属于**环境自动化**，不是 NPC 对话。依赖阶段的刷新要用项目状态守门，改动前先检查现有怪物数量（`MonGenEx`），有意识地清理地图或列表（`CLEARMAPMON`、`CLEARNAMELIST`），并在每个排程分支的预期动作后以 `BREAK` 收尾。
- 动态 NPC 由 `CreateNPC` 创建时，脚本文件放在 `Market_def`。最后一个参数为 `1` 时脚本文件名省略地图后缀（`英雄引路人.txt`）；为 `0` 时保留后缀（`英雄引路人-3.txt`）。

### 变量与语法

- 不要臆造变量前缀。使用自定义写法前，先从说明书或样本确认变量族；现有证据中 `R$...` 不是已收录的列表变量。
- 变量作用域与持久性见 `628-程序变量说明.md`：`G`/`A` 为全局且存档，`I` 为全局但重启重置，`P`/`D`/`M`/`N`/`S` 为私有临时族（重置点各异），`U`/`T`/`J`/`Z` 为私有存档或按日重置族。**按所需生命周期选族，不要图名字方便。**
- `S$...` 与 `N$...` 是 `788-扩展字符变量S和数字变量N.md` 收录的扩展字符/数字变量。作为命令参数传值时要写 `<$STR(S$变量名)>` / `<$STR(N$变量名)>`。
- `L$...` 是 `192-多元数组元素变量.md` 收录的数组/列表变量族。整组赋值用方括号，例如 `MOV L$地图列表 [0,1,D1002]`；读取用 `<$STR(L$地图列表[0])>`；按下标动态读取用 `<$STR(L$地图列表[<$STR(N$下标)>])>`。
- `P0`/`P` 变量**不跨** `[@OnTimerX]` 回调持久化；跨回调的计数器或占用状态要用**个人标识 `[n]`**（它会持久化）。因为它会跨重登存活，登录时必须显式重置。
- `DIV`/`MUL`/`MOV`/`INC`/`DEC` **不接受字符串变量**：写 `DIV N$X 5`（裸变量或字面量），绝不能写 `DIV N$X <$STR(N$X)> 5`。`SMALL`/`LARGE`/`EQUAL` 取 `变量 数值`，变量在前。`DIV` 是整除。
- 扁平 `#IF/#ACT` 块是**顺序执行，不是 else-if**。高等级对象会同时命中每一条 `#IF CheckHerolevel > N` 分支。做「由单一输入推导单一取值」的逻辑时，用算术（`MOV`/`DEC`/`DIV`/`INC`）配合 `SMALL`/`LARGE` 夹取，而不是扁平分支链；或者用 `#ELSEACT BREAK` 实现真正互斥的分支。
- LF 脚本的 `#IF` 是**独立的条件块**。后面的 `#IF` 不会自动被前面失败的条件保护；失败的前置检查必须用 `#ELSEACT BREAK`（可选配 `#ELSESAY`）阻断下落。付费随机尝试的写法是：一个块做 `CHECKITEM` 并给出失败原因和 `BREAK`，把 `TAKE` 放在该块的成功 `#ACT` 里，然后另起一个 `#IF RANDOM ...` 块。
- `RANDOM n` 是**条件/概率门**，不是赋值工具，在 Mir 类脚本里通常当作 `1/n` 概率门。不要把 `15/25/35/45` 这类百分比变量直接喂给 `RANDOM`，因为数值越大命中率越低。正向百分比门要用收录的 `RANDOMEX 子 母`，例如 `RANDOMEX <$STR(N$触发几率)> 100`；需要存下随机数值时用 `MOVR`。
- 互斥的百分比结果若需要存随机值，先 `MOVR N$随机 1 100`，再刻意安排阈值检查顺序。降序 `LARGE` 链且每个 `GOTO` 后跟 `BREAK`，能干净地映射成区间。**要按有序门重新推算实际区间，不要假定写下的数字就是百分比。**
- `GetRandomText` 用于把文件里的随机行读入收录的 `S`/`A` 变量（见 `438-取得随机字符串.md`）。候选是脚本内静态列表时优先 `L$`；只有候选确实该放文本文件时才用 `GetRandomText`。
- 脚本内随机取列表项：用 `MOVR` 生成下标，再按下标读 `L$`。样本 `样本Mir200/Envir/Market_def/酒馆/翔天-3.txt` 的写法是 `MOV L$合英雄 [...]`、`MOVR N$抽44 0 5`，然后 `GIVE <$STR(L$合英雄[<$STR(N$抽44)>])> 1`。
- 不要臆造函数式常量，例如 `<$MAPTITLE(<$STR(A91)>)>`。说明书在 `642-脚本变量大全.md` 中记录 `<$MapTitle>` 为**当前玩家所在地图名**、`<$HMapTitle>` 为英雄所在地图名，并没有收录「地图代码转标题」的参数化函数。脚本随机选目标地图代码又要播报其显示标题时，要从已确认的项目数据推导，例如维护一个与地图代码 `L$` 列表同下标的显示名 `L$` 列表（可由 `MapInfo.txt` 生成）。
- `GetStringPosEX` 是**条件命令**：放在 `#IF` 下，不要放进 `#ACT`。其路径标志要与路径形式一致（`..\QuestDiary\...` 这类相对路径用 `0`，绝对路径用 `1`）。当它把一行分隔配置返回到 `S$` 变量时，要用收录的 `ExtractStringEx` 拆分该行，不要指望 `GetListString` 填满两个以上输出变量。
- 金币检查用收录的条件命令 `CHECKGOLD 数量`，例如 `CHECKGOLD 20000`。说明书在 `knowledge_base/chapters/629-传奇脚本命令详解.md` 把它定义为条件命令（`checkgold 数值 ;拥有金币数>=数值为1否则为0`），所以它要放在 `#IF` 下，其后的 `#ELSEACT` 即金币不足路径。不要臆造 `CHECKITEM 金币` 检查——同章定义 `checkitem 物品 数值 ;测试拥用物品的数量`，测的是物品不是金币；也不要在 `CHECKGOLD` 能表达该守门时偏用裸 `<$GOLDCOUNT>`（`642-脚本变量大全.md` 记录它为当前金币数量常量）比较。（`628-程序变量说明.md` 只讲变量族与 `@@InPutString`/`@@InPutInteger`，**未收录** `CHECKGOLD`，引用时不要指向该章。）
- `FindMonPoint` 返回指定地图上最近的匹配怪物。定位面板要把每个显示变量初始化为已知兜底值（如 `未知`），只覆盖成功的匹配；后缀变体要写显式 `#OR` 检查，或仅在确实需要时用收录的忽略后缀计数命令。

### 参数化标签

- 形如 `@召唤配置(骷髅,1)` 的参数化标签，`<$SCRIPTPARAM*>` 是**标签局部**的。说明书 `787-扩展NPC脚本点击触发带参数-NPC标签带参数.md` 警告参数在跳转后可能被清空，所以在任何可能 `GOTO` 或触发其他标签的流程之前，先把参数拷进变量。
- 敏感的参数化标签，要在扣费、取物、发奖、转职、传送、改文件、改存档变量之前加 `CHECKSCRIPTPARAM` 白名单分支。本地 `样本Mir200` 常省略这道守门，所以那是**惯用写法而非安全基线**。
- 形如 `GOTO @label(args|retvars)` 的回调式辅助，被调用标签要配 `RETURN`，并记住 `RETURN` 会结束当前脚本段。同文件的计算/归一化辅助用这个；不要在没有说明书或本地样本佐证时假定存在未收录的 `#CALL [file] @label(args)` 直接传参。
- 参数用于选择文件路径、类别、物品、宠物或职业时，要**立即归一化**进 `S$`/`N$` 变量并校验允许值。不要让原始 `<$SCRIPTPARAM*>` 成为路径权威或破坏性操作权威。
- 对镜像地图脚本（如 `样本Mir200/Envir/Market_def/比奇城/火龙将军-0.txt`），`AddMirrorMap` 的最后一个参数是**变量名而非数值**；重建实例前要配显式清理与阶段标识。
- 组队传送要用 `GROUPMAPMOVE`，当地图归属或阶段检查重要时，不要用散落的传送分支替代。

### 脚本编辑写法

- 共享功能模块被众多 NPC 通过 `#CALL [系统功能\xxx.txt] @label` 调用时，某些项目要求最小化的包裹式调用文件布局：只有**第一个**标签需要在紧邻下方带 `{`，文件只需要在最后一个有效行有一个配对的 `}`。不要给后续每个标签都加花括号，也不要给每个标签局部「配平」。编辑邻近调用文件时保持或顺手规范化这个包裹结构，并让 NPC 文件保持为只派发到共享标签的薄菜单。
- 批量奖励循环（如 `样本Mir200/Envir/QuestDiary/系统功能/冶炼金矿.txt`）要在 `While` 之前初始化循环计数器，把守门分支与奖励分支分开，每个奖励计数器都要显式写回。
- 持久列表编辑器（如 `样本Mir200/Envir/QuestDiary/系统功能/老登辅助/存仓.txt`）用 `L$` 做内存列表操作，用文本文件做按角色的持久存储；渲染成 `S$` 文本与存储列表要分开处理。
- `ITEMBOX` / `BOXITEM` 流程要核查物品归属生命周期：确认框内物品存在，用 `SetUpgradeItem` 绑定，改动它，调 `UpdateItem`，再 `ReturnBoxItem`；**每一条会让物品留在框内的失败路径都必须归还它**。
- 脚本生成的装备若来源必须在客户端可见，要先绑定刚给出的物品再改动：`GIVE` → `LINKGIVEITEM` → `SetItemFrom -1 ...` → `updateitem -1` → `clearLinkItem`。说明书警告 `LINKGIVEITEM` 只绑定**最后一次成功给出**的物品，且必须配 `clearLinkItem`；还要确认登陆器/客户端提示文件暴露了 `[ItemFrom]` 与相关 `ItemFrom*` 文本标签。
- 双槽转移流程（如 `样本Mir200/Envir/QuestDiary/系统功能/装备转移.txt`）要把两个框当作**一次事务**审：校验兼容的 `<$BOXITEM[n].STDMODE>`，在随机成功前先扣费，读取旧附加值与新元素值，清空来源，应用到目标，有意识地复制物品状态/自定义文本，两边都 `UpdateItem`，并在每条终止路径上 `ReturnBoxItem` 或 `DelBoxItem`。
- 按 `397-自定义OK框.md`，同一交互面上要避免在 QFunction 与 NPC 脚本之间复用自定义 OK 框 ID。脚本序列化装备时，要把普通附加值、元素值、来源字段、自定义文本作为**独立区段**分别拷贝，然后显式更新或清空被绑定物品。
- `INPUTTEXT` / `INPUTNUM` 控件要把输入 ID 追到 `<$NPCINPUT(id)>` 以及命名该 ID 的提交按钮。官方输入章节仍要求脚本在服务端校验提交数据，所以不要只信客户端的 min/max 或提示文本。
- 穿戴中物品的服务收费（如 `样本Mir200/Envir/QuestDiary/系统功能/老登辅助/探测.txt`）要把 `CHECKITEMW` 与按位置的改动组合：检查已穿戴物品，执行动作，`ChangeItemDura <pos> - value`，`UpdateItem <pos>`，只有在后续持久检查确认耗尽后才用 `TakePosW <pos>` 移除。
- 宠物/随从存仓（如 `样本Mir200/Envir/QuestDiary/系统功能/老登辅助/存储仆从.txt`）要先从官方技能状态（`GetMagicInfo`）和当前随从数推导容量再改动状态。用 `CHECKSLAVENAME` 校验名字，用 `KillCallMob` 杀死存入的宠物，把 `L$` 列表持久化回存档变量或文本文件，恢复时用带显式所属技能类型的 `RECALLMOB`。
- 重生/洗职业流程（如 `样本Mir200/Envir/Market_def/云隐宗师.txt`）要先把参数拷进变量，再在 `CHANGEJOB`、`RENEWLEVEL`、`CLEARSKILL` 或删仓之前校验英雄状态、背包空间、等级上限与资源物品。
- 英雄侧命令常需 `H.` 前缀，如 `H.RENEWLEVEL`、`H.CLEARSKILL`、`H.TAKEBAGITEM`；假定玩家侧命令适用于英雄之前，先查对应说明章节。
- 管理/辅助菜单（如 `样本Mir200/Envir/QuestDiary/系统功能/帮助菜单.txt`）是**混合面**。把真实玩家入口与 `ISADMIN` 守门的 GM 探测、注释掉的测试调用、临时修复标签分开，再决定是否把其中写法提升为生产建议。

### 玩家可见文本

- 写 `MESSAGEBOX`、`SENDMSG` 或 `#SAY` 之前，先决定**哪些数字是给玩家看的**。玩家做决策需要的花费、奖励、所需材料、剩余次数和明确的失败原因要展示；调参用的开关（PK 阈值、惩罚增量、概率削减、定时器 tick 计数、维护细节）应作为脚本内部数据，除非该界面明确是 GM/管理专用。不需要精确数字时，优先用贴合世界观的表述，而不是暴露 `PK值+160` 这种公式。
- 反复调的游戏数值（PK 上限、单次惩罚、价格、奖励上下界、冷却 tick、概率阈值）要在入口或结算标签附近**一次性赋给局部扩展变量**，例如 `Mov N$红名PK值 200`、`Mov N$黄名PK值 160`、`Mov N$一次PK值 40`。在检查、改动、需要精确值的消息和最终守门分支里统一用 `<$STR(N$变量名)>`，这样后续调平衡不必到处找魔法常量。

### 功能链路与安全

- 可解锁的玩家功能，编辑前要追完**整条链**：任务页提示（`QMission-0.txt`）→ 教学 NPC → 存档个人标识（`CHECK [n]` / `SET [n]`）→ 共享功能脚本守门。即使菜单只在学会后出现，真正的动作标签也必须守门，并在任务页镜像完成文本。
- PK 值驱动的犯罪/风险系统，要把 `CHECKPKPOINTEX` 与 `CHANGEPKPOINT` 章节交叉核对，阈值与惩罚放在局部 `N$` 变量里，最终惩罚守门要同时兜住 `=` 与 `>` 阈值两种情况。不要让辅助/挂机功能在没有明确设计豁免的情况下绕过同一套犯罪策略。
- 面板类功能（如 `样本Mir200/Envir/QuestDiary/系统功能/老登辅助/辅助.txt`）要把 UI 标识与动作标签当**一张映射表**读：`<$flag(n)>` 渲染当前状态，`check [n]` 选择切换分支，`SET [n]` 写入状态，`reset [start] count` 可清除连续标识区间。
- 按角色计费的辅助开关，状态需跨重登时优先用 `U10` 这类存档私有变量。在辅助面板加开关，启用时用 `CHECKGOLD 数量` 守门，切换时重置 tick 计数器，功能不该打断游戏时用 `SENDMSG` 做非阻塞的状态/失败提示。
- 已有共享毫秒定时器（如 `TimerEx7`）在驱动流程时，不要为了加一个更慢的周期扣费而改它的间隔。保持原 `SETONTIMEREX` 间隔，加一个小的按角色计数器，每 N 个 tick 才执行付费动作；起点与 `MapQuest_def/QManage.txt` 里的 `#CALL` 要配到一个专注的辅助标签。
- 攻击触发里的保护逻辑，先用 `CHECKCURRTARGETRACE = 0` 确认当前目标是玩家，再用 `C.` 语法读取目标玩家的存档状态，如 `EQUAL <$C.STR(U10)> 1`。**设计是按角色时，不要用另一个全局变量替换全局开关。**
- `ChangeState` 要先确认**当前脚本主体**。无前缀的 `ChangeState` 作用于该主体，不会自动作用于当前攻击者或当前目标；在 `[@Struck]` / `[@StruckDamage]` 回调里它通常作用于被击中的玩家。只有在确认目标语境后才使用 `M.`、`H.`、`FS.`、`BB.` 这类已收录前缀。
- `ChangeState` 效果码（出自说明书）：`1` 石化、`2` 冰冻、`3` 蛛网、`4` 红毒、`5` 绿毒、`6` 定身、`7` 瘫痪、`8` 禁锢别人、`9` 防禁锢、`10` 吸血、`11` 吸蓝、`12` 禁锢自己、`13` 间隔掉血、`14` 禁止使用技能。效果 `1-5` 的参数 3 控制是否检查对应抗性/免疫（`0` 不检查，`1` 检查）；时间设为 `0` 即清除该状态。装备驱动的触发仍要在调用前守门已穿戴物品/部位、职业、来源对象、概率与冷却。

### 计时器与死循环

- 报 `[脚本死循环] ... 命令:GOTO @label` 时，**不要把被点名的标签或 `GOTO` 这个词当作递归环路的证据**。先经 `QManage`、`#CALL`、`GOTO` 重建完整进入路径，再区分「无界环路」与「合法路径超了配置的跳转预算」；该路径可能是无环的，或含可证明有界的循环。参见 `references/script-deadloop-debugging.md`。
- `!Setup.txt` 里 `ScriptGotoCountLimit` 与 `LimitScriptGotoCount` 同时存在时两个都要审。其生效行为可能依引擎版本而异；一个很大的历史值**不能证明**后来设的低限值未生效。让生效上限保持有限，并且只在削减了可避免的高频工作之后，才把它提到实测合法路径之上。
- 不要把同文件内的 `#CALL` 批量改写成 `GOTO` 当作死循环修复。说明书收录的是 `GOTO` 标签派发与回调式 `RETURN`，而项目日志可能把被调用的标签报成 `GOTO`；改拼写并不能证明递归或跳转预算消耗减少了。除非有经验证的引擎规则要求转换，否则保持既有的调用语义。
- 不带执行次数参数的 `SetOnTimer` 会**无限重复**直到 `SetOffTimer`。高频处理端应做廉价的状态检查，只在已装备对象变化或生命周期事件置了脏标志时才调完整刷新。加 `BREAK` 或阻止重复注册定时器，**不会**减少已在重复的定时器所做的工作。
- 把重复的完整刷新换成脏检查时，要审计旧刷新在续期的每一个显式时长效果与周期动作。把 `ChangeHumAbility`、`AddHumNewValue`、`ChangeSpeed`、`ChangeState` 的时间参数当作**租约**：状态变化保留完整刷新，另加一个小的「未变化续租」标签处理租约与有意的周期工作，并在清理时停掉定时器让租约自然到期。除非每条移除路径都能安全地只移除该功能自己的贡献，否则不要把这些效果改成永久。

### 英雄与宝宝

- 说明书「英雄命令通常加 `H.`」是**弱启发式，不是证明**。`H.RECALLMOB` 在实机可用，但 `H.CHECKSKILL`、`H.CHECKSLAVECOUNT`、`<$H.SlaveCount>`、`H.KILLCALLMOB`、`H.CLEARSLAVE` **不存在**。每条英雄侧命令都要对着说明书或实机验证后再用；当某命令既无说明书页也无项目先例时，**在真实测试证明之前一律假定它不存在**。
- `[@HeroMagSelfFuncX]` 在 `832-英雄魔法触发功能.md` 有收录，但在实机上**没有**为英雄召唤技能触发。英雄魔法自触发视为版本相关；某技能必须设置状态时，用 `[@HeroLearnMagic]` 配 `<$H.LearnMagicID>` 作为可靠的学会时机钩子。
- **没有**引擎命令能读英雄宠物数量，也没有命令能删除已召唤的英雄宠物。用专用个人标识 `[n]` 当槽位来表示宠物占用，登录时与 `@OnHeroSlaveDie` 时重置；清理要偏向多清状态（**少召唤可接受，溢出不可接受**）。溢出只能靠英雄死亡、换图或 GM 击杀来清。
- 英雄宠物等级由主人等级推导时，用 `MOV N$级 <$H.LEVEL>` 然后 `DEC`/`DIV`/`INC`，并用 `SMALL N$级 1` / `LARGE N$级 7` 夹取。完整的英雄自动召唤范式见 `references/hero-autocall-slave.md`。
- `H.ChangeHumAbility ... 3` 是**租约而非永久写入**。效果需要持续时，要给它专用的续期定时器与重建路径；不要假定一次刷新能扛过引擎自己的周期性重算。
- 某些项目中 `LockUpdateAbil` 若被长时间跨在刷新链上，会卡住英雄或宠物移动。锁的作用域要尽可能小，与紧随的 `UpdateAbil` 配对；功能只需最终赋值时，优先用无锁刷新。
- 英雄装备驱动的持久 BUFF，要把英雄的装备/卸下/登录/死亡/定时/攻击/受击路径当作**一个生命周期**而非孤立回调。英雄状态放在自己的 `N$英雄*` / `S$英雄*` 命名空间，从 `@HeroTakeOnEx`、`@HeroTakeOffEx`、`@HeroLogin`、`@HeroDie`、`@HeroStruckDamage`、`@HeroAttackDamage` 刷新，并在 14 槽物品变化或消失时清掉定时器与缓存状态。

### 赋值型命令与倍率

- 覆盖整个属性的赋值型命令（如 `ChangeSpeed` 或 `H.CHANGESPEED`），**绝不允许**登录、装备、BUFF 或功能脚本写入互相竞争的最终值。每个来源保留一个贡献变量，状态变化时重置/重算聚合值，每个脚本主体只下发一次最终赋值。玩家用 `ChangeSpeed`，英雄用 `H.CHANGESPEED`；这是**不同主体**，各需自己的最终写入标签。功能被移除时，把它的贡献设回 `0` 并调用同一个聚合器；不要靠在别的分支里只赋一个基础值来撤销。
- 设置整个倍率的脚本倍率命令（如 `KILLMONEXPRATE`、`POWERRATE`、`KILLMONBURSTRATE`），要把**覆盖型来源**与**加算型元素来源**分开。活动、消耗品、称号/排名、永久码收益应写各自的贡献变量并调用同一个最终结算标签来下发胜出/聚合的命令值；说明书定义为加算的装备、军鼓与隐藏元素加成（如 `AddHumNewValue 26` 杀怪经验倍率、`AddHumNewValue 11` 杀怪爆率）应留在加算层，不要再下发一次直接的倍率命令。
- 攻速平衡实现要把职业基础与路线/BUFF 贡献分开存储，例如 `N$职业基础攻速`、`N$路线攻速`、`N$最终攻速`，用收录的 `FORMULATION` 组合，并让登录、刷新、路线切换、清理都调用同一个重算标签。重算要先按目标主体/职业守门，**避免非目标职业落到零值最终写入**。功能模块可以更新自己的贡献，但**不得**再加一次直接的 `ChangeSpeed 2` 或 `H.CHANGESPEED 2` 赋值。

### 功能型 BUFF 与职业路线

- 功能型 BUFF 的技能覆盖范围，要查**项目自己的 `Magic` 表**，不要凭记忆或熟悉的 Mir 技能列表。只有项目 DB 里存在的玩家技能才能成为对玩家的承诺；英雄专属技能名不能宣传成玩家路线触发，除非设计明确面向英雄。
- 需要怪物侧可见状态的功能 BUFF，优先用收录的目标/效果命令而非假技能施放。`RangeHarm` 在参数 8 设为 `2` 时可以对怪物造成伤害并附加状态；某条满层路线需要可见地标记受影响怪物又不想放出 `火墙` 这类持续技能时，用收录的效果码如 `8`（冰冻）和 `10`（红毒）。
- 补偿宠或路线召唤宝宝，要从项目 `Monster` 表里选**精确怪物名**，对比其等级/HP/攻击与原生召唤宠，除非有意为之，否则避免复用过强或核心职业召唤。每次 `RECALLMOB` 都要按补偿宠的精确名用 `CHECKSLAVECOUNT` 守门，加显式冷却变量，并在路线关闭或切换时用 `KillCallMob` 清理路线自有宠物。
- BUFF/头顶图标美术资源，写脚本数字前要确认资源表的**索引基**。某些项目里 `EffectImageList.txt` 的图片文件引用被修正为从 `0` 开始，所以 `SetArrBuff`/`SETICON` 的文件索引应遵循本地表而非假定 `1`；重建前清掉陈旧图标（`CloseArrBuff`、`SETICON n -1`），并且不要把聊天 `SENDMSG` 或阻断分支的 `BREAK` 放进刷新/辅助路径里，因为定时刷新或后续描述分支仍需要运行。
- 面向玩家的 `SetArrBuff` 悬停文本与 `ItemDescList.txt` 备注要保持在**玩法层**：已装备部位、方向/流派、触发技能、可见效果、品质解锁、玩家反馈。不要暴露开发维护细节，如刷新间隔、临时属性时长、审计/复查措辞、清理内部逻辑、脚本恢复或诊断记录，除非该界面明确是 GM/管理专用。
- 功能触发聊天的反馈，要用项目里已在控制同类玩家提示的**静默标识**。不要未经核对本地辅助脚本就复用不相关的静默标识。
- `样本2Mir200` 的目标侧减益，要一致地使用目标前缀（`M.` 或命名玩家前缀），写目标侧标记如 `S$咒蛊术`，显示目标侧 BUFF 图标，并强制目标侧重算。样本范式包括 `咒蛊术`、`体态压迫`、`撕裂`、`失心锁`、`邪爆符`。
- `样本2Mir200` 的「铭文」或隐藏属性分析，至少要交叉核对 `CustomItemPropertyTextVarList.txt`、`ItemDescList.txt`、相关 NPC 脚本、`QFunction-0.txt`、攻击触发、`GroupItemList.txt`、`GroupItemSkillPowerList.txt`、`SkillPowerItemList.txt`。`ItemDescList.txt` 是**发现面**，不是运行时效果的证明。
- `样本2Mir200` 里功能型 BUFF 通常是**一条链**而非单个文件：`MerChant.txt` 条目 → 流派/功能 NPC → `QFunction-0.txt` 回调 → `QuestDiary/游戏登陆/登陆脚本.txt` 重算标签 → 攻击/技能触发 → 物品/套装显示表。声称某个 BUFF、铭文或隐藏属性已生效前，要顺着这条链走完。
- `样本2Mir200` 的流派与觉醒系统，把 `QuestDiary/游戏登陆/流派BUFF读取.txt` 当作派发端、`QuestDiary/游戏登陆/登陆脚本.txt` 当作属性重算中枢。功能脚本应改动状态，然后只调用受影响的那几个读取器，例如 `@_@元素读取`、`@_@攻魔道读取`、`@_@HPMP读取`、`@_@防御读取`、`@_@攻速读取`、`@_@施法速度`、`@_@吸血读取`、`@_@技能等级读取`、`@_@技能威力读取`、`@_@BB读取`。
- `样本2Mir200` 的限时 BUFF 与减益，每个影响属性的 `SetArrBuff` 都要配一个 `[@CloseArrBuffX]` 清理，清除标记/计数器并重跑受影响的读取器。`苹果`、`满江红`、`幸运药水` 这类持久 BUFF 会存到期状态并在登录后重建图标；**图标本身不是真相来源**。
- 装备槽驱动的持久 BUFF，要在刷新前和战斗触发前确认已装备位置，非倒计时自身图标用 `SetArrBuff` 第 5 参数为 `-1`，并且只按按钮号关闭自动排列图标，例如 `SetArrBuff 1 87 ...` 对应 `CloseArrBuff 87`；该模式**不要**用组+按钮形式 `CloseArrBuff 1 87`。
- 装备槽驱动的持久 BUFF，要把卸下、物品掉落、持久耗尽、脚本侧移除、死亡检查、登录刷新、定时刷新当作**同一个生命周期**。已装备物品缺失或变化时，模块必须关闭、清空功能变量、停止刷新定时器，并在任何后续刷新重建它之前关闭图标。

### 颜色

- Mir200 颜色值是 `0-255` 的**数字色板 ID**，不是任意 RGB 输入。做颜色相关工作时，先看 `references/mir200-256-colors.md` 与官方颜色章节再选数字。
- 本地 `256色值` 来源**跳过了颜色 `32`**；除非另有官方项目来源确认其含义，新脚本不要用 `32`。颜色 `255` 在最终表格里表现为没有显式 HTML `bgColor` 的白色格，所以不要求精确白色文字时优先用已确认的 `246`/`254`。
- 有样本支撑的可用预设：物品备注 `218`，套装备注启用/未启用 `223,249`，装备或套装物品名 `116`，正向/成功数值 `250`，危险/未启用/Boss 警示 `249`，黄色标题或计时 `251`，品红稀有提示 `253`，青色标签 `254`。

## 项目知识工作流

在 Mir200 仓库里工作时，动手前先建一个小的项目模型：

1. 读仓库说明文件（通常是 `AGENTS.md`），了解编码、编译/运行限制、归属边界与静态检查方式。
2. 读用户提到的设计文档，然后若需求引用了某功能名，在 `docs/` 里搜邻近规格。
3. 把耐久事实提取进工作笔记：阶段变量、地图组、关键入口脚本、触发标签、说明章节、验证命令。
4. 这些事实若可跨任务复用，就把规则写进本技能或某个 reference 文件，**而不是写会话叙述**。
5. 若某 Mir200 项目对同一个 GitHub 仓库同时配了 HTTPS 与 SSH remote，而 HTTPS 报 `Failed to connect to github.com port 443`，先确认分支与 remote URL，然后通过已配置的 SSH remote 推同一分支，而不是改代码或重写历史。

## 脚本深挖工作流

用户点名一个 Mir200 样本脚本要深度学习时：

1. 先对它跑 `learn-script`。
2. 按此顺序读报告：标签、调用、标识、输入控件、物品框、定时器、变量、说明主题、学习笔记。
3. 把报告中每个说明主题对照官方章节核实，再转成建议。

5. 脚本专属观察记进 `references/script-deep-dives.md`。
6. 训练产物保持小而可复用；不要把整段脚本拷进技能。

## 高效编辑指引

- 涉及 GBK 安全的 Mir200 编辑时，优先用仓库里已有的可复用工具，尤其是批量替换、`MapInfo` 解析、阶段检查、怪物 DB 检查、Boss 分类与编码检查。
- 工具尚不存在且任务会重复时，建议或创建小的 `tools/` 脚本，而不是不断膨胀一次性 PowerShell 片段。
- UTF-8 的 Markdown、JSON 与小的纯 ASCII 配置改动，用常规补丁编辑即可。
- 生成的 Mir200 脚本块，要用定向静态检索验证命令计数、标签唯一性、`#CALL` 目标以及剩余绕过路径。
- 改动 `QMission-0.txt` 时，要对新增显示标签静态检索 `GOTO @...`；除非同一文件里已有可用实例证明该引擎语境支持，否则不要在任务页显示流程里用它。

## 训练工作流

用户要求本技能从 `样本Mir200` 或真实 Mir200 项目**学习、训练、自升级、提炼可复用经验**时，用这个循环：

1. 跑 `update` 重建索引、思维摘要与训练课程。
2. 查看 `references/mir200-training.md`。
3. 一次只取一课，从入口/派发开始，到组合系统结束。
4. 查看列出的样本文件，写下：入口、守门、动作、状态写回、失败路径。
5. 把观察转成建议之前，先对照 Markdown 说明书核实命令语法。
6. 真实项目还要看 `AGENTS.md` 与相关 `docs/*.md`；把仓库专属规则提取为项目事实，只有可跨项目复用的耐久经验才提升进本技能。
7. 继续开放式的样本训练时，按命令多样性、触发覆盖、状态写入与说明书交叉核对价值给候选打分；**避免反复研究近乎重复的商店/仓库脚本**。
8. 跑 `update` 更新生成的摘要；只有耐久工作流规则才手改 `SKILL.md`。

不要把运行日志或二进制/服务端文件当训练材料。优先 `Envir/Market_def`、`QuestDiary`、`MapQuest_def`、`Robot_def`、`MapInfo`、`MapEvent`、`MerChant`、`Npcs`、`MonGen` 相关文件。

## 命令

在任意目录运行；显式 `--root` 保证技能不受当前工作目录影响。每个会话设一次 `$KB` 让命令更易读：

```powershell
$KB = "<skill-dir>"
```

```powershell
# 维护
python "$KB\scripts\lf_kb.py" --root "$KB" update
python "$KB\scripts\lf_kb.py" --root "$KB" validate

# 检索：说明书、样本脚本、MapInfo 链接，或全部
python "$KB\scripts\lf_kb.py" --root "$KB" search "CHECKITEM GIVE 装备回收" --source all --limit 8
python "$KB\scripts\lf_kb.py" --root "$KB" search "MAPMOVE" --source sample --limit 5
python "$KB\scripts\lf_kb.py" --root "$KB" search "0 308 264 0102" --source mapinfo --limit 5

# 读取单个文件（说明书章节、样本脚本或 reference）
python "$KB\scripts\lf_kb.py" --root "$KB" inspect "knowledge_base/chapters/661-丢弃背包物品前触发.md"
python "$KB\scripts\lf_kb.py" --root "$KB" inspect "references/mir200-thinking.md"

# 深挖单个脚本：标签、调用、标识、定时器、变量、说明主题
python "$KB\scripts\lf_kb.py" --root "$KB" learn-script "样本Mir200/Envir/QuestDiary/系统功能/装备转移.txt"
```

两点实用提醒：

- `search` 每条命中都带 `text` 字段，控制台输出可能很长。已知功能是项目专属时，优先 `--limit 5 --source sample`。
- 用户点名某个脚本时，**第一步就该跑 `learn-script`**。它一次给出标签、调用、标识、输入控件、物品框、定时器、变量与匹配的说明主题，比从头到尾读一个大脚本便宜得多。

## 样本索引的排除范围

样本索引**有意跳过**实机服务端的一部分内容，因为那部分会淹没检索结果却不携带可复用的脚本知识：

- 运行产物与二进制：`Log`、`ConLog`、`Map`、`M2Data`、`Castle`、`GuildBase`、`Notice`、`Share`、`ShareV`、`Sort`、`PlugClient`、`Market_Saved`、`Market_Prices`、`MasterNo`、`MonIcons`、`NpcIcons`。

  注意这里只排除人为复制命名，**不排除**引擎意义上的「副本地图」相关文件，所以正常脚本不会被误伤。

如果检索某功能返回空、但你明明能在磁盘上看到它，先检查该文件是否命中了上述规则，再下结论说不存在。必要时直接对真实路径用 `inspect`。

## 维护

自我升级就是从当前说明书与样本脚本刷新派生索引：

```powershell
python "$KB\scripts\lf_kb.py" --root "$KB" update
python "$KB\scripts\lf_kb.py" --root "$KB" validate
```

服务端发生影响脚本结构的变动后要跑 `update`——新增目录、新增 NPC 文件、编辑 `MapInfo.txt` 链接等。它重建 `docs.json`、`sample.json`、`mapinfo-links.json`、思维摘要与训练课程大约只需一秒，所以长时间编辑过程中**没有理由让索引陈旧**。

若 CHM 重新转换过，先跑项目的转换脚本，再跑本技能的 `update`。

更新后，以重新生成的 `references/mir200-thinking.md` 作为本地思维摘要。它应当由真实脚本更新，**不是凭记忆**。

把 `references/mir200-training.md` 当作持续改进的课程地图。每课都列出信号、样本文件与阅读重点，未来的 agent 无需原始转换语境也能继续练习。

## 回复规则

- 引用所用的本地 Markdown 章节或样本文件。
- 区分「说明书官方行为」与「基于样本脚本的推断」，并说明样本来自哪个服务端。
- 没有匹配的说明书条目、答案来自样本推断时，要明说。
- 答案依赖重复出现的脚本范式时，要用平实的 Mir200 术语解释该范式，而不是只列命令清单。
